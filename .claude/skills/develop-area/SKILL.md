# Develop Area

Turn one row of the world-planning spreadsheet into a fully-built cluster of rooms, appended to the running world draft. This does one area per invocation — do not chain multiple areas into a single pass unless the user explicitly asks for that.

## Inputs

1. **The two planning spreadsheets.** Look first in `/mnt/c/Users/Joe/Downloads/` for files matching `*gomud-world-grid*.csv` (the 10x10 spatial layout) and `*gomud-world-details*.csv` (columns: `Area name, Theme, Connections, Enemy level ranges, Sub-areas`). If neither glob matches anything, ask the user where the current exports live — they're Google Sheets downloads and may be re-exported with a slightly different filename each time.
2. **The running draft**, `data/rooms.draft.json` at the repo root. This accumulates every area built so far. If it doesn't exist yet, seed it from `data/rooms.json`. Never write to `data/rooms.json` directly.
3. **The target area name**, passed as the skill argument. Match it against the details CSV's `Area name` column (case-insensitive, tolerate minor punctuation differences).

## Process

1. **Look up the row.** Pull `Theme`, `Connections`, `Enemy level ranges`, and `Sub-areas` for the target area from the details CSV.
2. **Check for duplicates.** If rooms whose name starts with `"<Area name> - "` already exist in the draft, stop and ask the user whether this is intentional (re-pass) before overwriting/adding more.
3. **Size the pass.** Parse `Enemy level ranges`. The first comma-separated entry (no trailing name) is the main zone's level span; any later entries with a trailing name (e.g. `"5-8 Barrow Depths"`) are a **named sub-area's** own level span. For each:
   - Main zone and any **non-town** sub-area (i.e. not parenthetically marked `(Town)` in the `Sub-areas` column): target room count = `levels_covered * 5` (mid-point of the user's established 3–7 rooms/level range). Levels covered = inclusive count, e.g. `5-10` = 6 levels.
   - Any sub-area marked `(Town)`: rooms are NOT level-scaled — use a flat 5–10 rooms (a plaza/hub plus a small handful of buildings) regardless of level span, since a town's size reflects its role as a hub, not its danger.
   - State the computed target(s) in your final summary so the user can course-correct next time, but don't stop to ask — proceed with the mid-point default.
4. **Find attachment points.** For each entry in `Connections`:
   - If that neighboring area already has rooms in the draft, find its existing degree-1 "edge" room facing this direction (name/description usually says so, e.g. "Northern Edge", "Southern Edge" — search for it; if more than one plausible candidate exists, ask which to use). Add a **new exit from that existing room** into the new area's first room, and a reciprocal exit back. This is how Tableland attached to Slime Forest's existing room 19.
   - If that neighboring area is not built yet, end the new area's graph on that side with its own single-exit "edge" stub room (name pattern `"<Area> - Path - <Direction> Edge"`), left dead-ended for whoever builds that neighbor next.
   - Whichever case applies, the direction word you use (east/west/north/south) must match that neighbor's actual position on the world grid CSV — check it, don't assume. This is what broke in Slime Forest: content built before its neighbors existed had exits that no longer made geographic sense once Seneca Downs and Morass were attached on specific sides.
5. **Design the room graph.** Not a straight line — mix hub rooms (3–4 exits) with dead-end spurs, matching the branching style already used in Slime Forest and Tableland. Give named sub-areas (formal ones from the `Sub-areas` column, and informal POI clusters you invent to dramatize the theme) their own nested name segment and their own small internal cluster of rooms rather than scattering them through the main zone. A dead end's *premise* has to justify being a dead end (see the realism check in step 7) — don't describe a room as a well-worn thoroughfare and then give it one exit.
   - **Environmental gradient.** If the zone borders two different neighbors (e.g. a swamp on one side, farmland on the other), the terrain should trend toward each neighbor's theme along the route that leads there — damp/muddy toward a swamp, drier and grassier toward farmland — not be assigned arbitrarily.
   - **Secret exits are a good recurring device** (a non-cardinal key hidden behind a gap/crack/squeeze), but the room behind one needs to feel like a genuine discovery — not a reskin of a prop already used elsewhere nearby.
6. **ID numbering.** Continue from `max(existing room ids) + 1` and `max(existing npc ids) + 1` in the draft. Never reuse or renumber existing ids.
7. **Write descriptions and exits.**
   - 1–2 sentences per room description, present tense, evocative but terse (e.g. "Slabs of rust-colored rock jut up at odd angles, as if the ground itself buckled long ago."). A second atmospheric line via `\n` is fine but not required every room.
   - **Never reference the NPC that spawns in a room** — a room's description describes the place, not whichever creature currently occupies it, since NPCs aren't guaranteed to stay in their spawn room. Give the NPC its personality through its own `description` and an on-enter `behavior` emote instead (see step 8). Ambient, plural, non-specific populace lines (e.g. "several devotees kneel here in quiet prayer") are fine, since they don't depend on one particular NPC's continued presence — the line to watch for is anything singular/specific ("something shifts," "a lone figure watches," "a sentry stands guard") that's really just describing the one NPC in disguise.
   - **Never imply a specific direction of arrival** — no "back to X," "the way you came," or similar, in either room or exit text. Most rooms are reachable from more than one direction or order of traversal, and this kind of phrasing is only ever correct for whichever direction the writer had in mind.
   - **Exit key convention**: every exit's key must be visibly parenthesized in its own description — `"(E)ast..."`, `"Squeeze through the (g)ap..."` — even for custom, non-cardinal keys. If the key letter doesn't appear capitalized in the text, there's no way for a player to discover it. Never invent a key whose letter isn't present in its own description.
   - **Cardinal vs. non-cardinal**: use plain compass directions for overland exits. Indoors (buildings, town interiors) and dark/underground spaces (dungeons, caves, trenches) should prefer non-cardinal, landmark- or verb-based keys instead — "north" doesn't intuitively apply to a hallway or a lightless cave.
   - **Compass accuracy**: reciprocal exits within a local cluster must actually point at each other (an `e` exit from room A to room B should be answered by a `w` exit from B back to A, or at minimum shouldn't contradict it), and any exit crossing into a different built area must match that area's real relative position on the world-grid CSV.
   - **Realism check**: a room's stated premise (sealed, hidden, well-worn, dead-end) has to be consistent with how and why the player can actually reach it. Don't describe something as "sealed" if the player can just walk in with no explanation of how.
   - World fact: **metal is rare/expensive** in this setting. Don't casually imply common metal objects or finishes (a wooden fence's posts shouldn't be "silvered," etc.).
8. **Populate NPCs.**
   - Not every room needs one — roughly 65–75% is the established density; pure connector/path rooms are often bare, named clearings/POIs almost always have one.
   - **`class` must already be registered in `classes.ByName` (`classes/classes.go`) before you use it.** This is the single most important rule in this file: the engine's class lookup has no fallback, so an unregistered class name causes a nil-pointer panic the instant the server tries to spawn that NPC — not a graceful failure, a crash on startup. Check first (`grep` the class name against `classes/classes.go`). If nothing existing fits the creature, add a new `Class` to `classes.go` in the *same* pass, following the growth-stat tiering already established there (roughly: weak/common fauna ~12–18 Det with a 3–6 primary stat; moderate ~20–28 Det with a 6–9 primary stat; strong/dungeon-tier ~28–38 Det with a 9–13 primary stat; boss/elite ~55–70+ Det with an 18–25+ primary stat) — and register it in the `ByName` map.
     - Before reusing an *existing* class for a new or reworked NPC, check what else already uses it (`grep` its name across `rooms.json`). Reusing for mechanical convenience is fine; reusing in a way that would misrepresent the new creature's actual species/type is not (a badger is not a boar), and upgrading a shared class's stats to make one NPC tougher will silently buff every other NPC using it too.
   - Give NPC `class`/flavor that embodies the zone's theme and, where the theme calls for variety, spread that variety across the cluster rather than repeating one archetype.
   - **Level should track the creature's perceived power** — what its name/description/class actually suggest — not its distance from the entrance. A weak flavor creature (a mouse, a goat) should just be level 1 regardless of where it sits in the graph; escalation within a zone should come from introducing genuinely different, tougher creature types deeper in, not from inflating weak creatures' levels uniformly by graph position. After assigning levels, sanity-check the *aggregate* feel of any long linear stretch — even a low-level entrance path benefits from one or two genuinely tougher side/spur encounters so it doesn't read as monotonous.
   - Baseline `exp_given = level * 5` (matches the game's actual established rate — do NOT use `level * 10`, and do NOT use the Slime Castle boss numbers as a scaling reference; those are a deliberate joke specific to that area). A deliberate elite/mini-boss can carry a 2x–3x multiplier on top of the baseline. A zone's **capstone boss** can go further, up to roughly 2x–10x, reflecting that bosses are meant to be a disproportionate payoff relative to reaching them — eventually gated behind an aggressive, on-sight guardian (so the boss can't just be run past), and respawning far less often than regular NPCs. The gating and respawn-rate pieces depend on engine features that don't exist yet (conditional/gated exits, an attackable-on-sight NPC behavior); until then, a pass can only set this up narratively — placing a guardian NPC in the room before the boss, as Barrow Guardian already does for the Rockbound Barrow King — not mechanically enforce it.
   - Add a `behavior` block (pc-enters/pc-leaves `say`/`emote`) on roughly 1 in 4–5 NPCs — the standout ones — not all of them. When you do, write the NPC's own `description` so it sets up what the emote pays off, rather than being generic flavor text bolted onto an unrelated action (the Wandering Shepherd — "watches the fields more closely than he watches you" paired with an emote of him doing exactly that — is the reference example).
9. **Merge into the draft.** Append the new rooms to `data/rooms.draft.json`'s array (plus the one or two modified existing edge rooms from step 4), preserving everything already there.
10. **Validate.** Run, in order, and fix any failure before finishing — do not report the pass as done if any of these fail:
    ```sh
    python3 .claude/skills/develop-area/validate_rooms.py data/rooms.draft.json
    go build ./...
    go test ./...
    ```
    Then do a live boot smoke test: copy the draft to `data/rooms.json` (or a temp copy pointed at by a throwaway config), start the server, and confirm it logs `Hosting on:` with no panic. The JSON validator only catches duplicate/dangling ids — it has no way to know if an NPC's `class` field is actually registered, which is exactly the kind of bug that only surfaces at runtime.
11. **Report.** Summarize: room-id range added, room/NPC counts, the computed size target(s) from step 3, which attachment points were wired and which were left as stubs for future areas, and any new classes added to `classes.go`. Remind the user they can open `tools/room-editor.html` (Load JSON → `data/rooms.draft.json`) to review and edit the result.

## Conventions this skill must follow

- Naming: `"<Area> - <Subarea>"` for named places, `"<Area> - Path - <Subarea>"` for connective/transitional rooms — both formal `Sub-areas` entries and informal POI clusters you invent use this same nested pattern.
  - Reserve the bare `"<Area> - <Name>"` form for a real multi-room cluster (Ritual Circle, Sunlit Shrine, Seneca Town) or a genuinely singular bridge/dungeon-entrance room (Standing Stones Circle). A standalone landmark hub that's really just a beefed-up path junction — one room, no cluster around it — should get the `"<Area> - Path - <Name>"` form like its neighbors; giving it its own orphaned tag reads as a "floating," disconnected room even though it's surrounded by the same area.
- Exits are bidirectional by default; a one-way exit (like the `??? - Cave`'s portal back to room 1) is the exception and should only appear when the theme specifically calls for a one-directional effect.
- Room ids and NPC ids are both drawn from a single global counter across the whole world — never restart numbering per-area.
- `data/rooms.json` is the live/canonical file the game server reads — this skill only ever touches `data/rooms.draft.json`. Promoting a draft to canonical is a separate, explicit step the user asks for later.

## Notes

- If an area's `Connections` field lists more than one neighbor (e.g. Saffron Coast connects west to Seneca Downs and east to Vermelico Sea), handle each independently per step 4 — some may attach to existing zones while others become new stubs, in the same pass.
- The Tableland pass (rooms 19–48 in the current draft) is the reference example for tone, density, and graph shape if you want to sanity-check a new pass against it.
